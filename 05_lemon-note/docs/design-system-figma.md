# Figma 디자인 시스템 — 컬러 변수화와 코드 패리티 감사

- **기간**: 2026-07-27 ~ 2026-07-29
- **상태**: 완료 (10개 페이지 전수 점검·수정)
- **대상**: 디자인 시스템 Figma 파일 (LN 00 ~ LN 09) / 기준 코드 `local-worker/web/`

## 왜 이 작업을 했는가

이 Figma 파일은 참고용 시안이 아니라 **구현된 코드를 문서화한 명세**다. 규칙이 하나 있다 —
*"모든 값은 `web/styles.css` · `web/app.js` · `web/index.html` 에서 추출한다. 코드와 다르면 코드가 맞다."*

그런데 값이 hex 로 하드코딩돼 있으면 이 규칙이 지켜지는지 확인할 방법이 없다. 색을 변수로
바꾸면서 전수 대조를 했고, 그 과정에서 **코드와 다른 곳이 계속 나왔다.** 아래가 그 기록이다.

가장 위험했던 두 건은 개수나 라벨이 아니라 **보고 구현하면 틀린 결과가 나오는** 오류였다.

## 6. 검증 방법 — 재사용 가능한 부분

**육안 대조는 이번 작업에서 네 번 틀렸다.** 다음 세 가지가 실제로 문제를 잡았다.

### 미바인딩 감사

페이지별로 모든 `fills`/`strokes` 를 훑어 변수에 안 묶인 페인트를 센다. **누락은 잡지만
"토큰은 맞는데 잘못된 토큰"은 못 잡는다** — `ink-400` ↔ `ink-500` 이 바로 그 사례다.

### 팔레트 대조

실제 빌드 스크린샷과 Figma 렌더에서 각 토큰 hex 의 픽셀 존재 여부를 세어 집합을 비교한다.
`ink/500` 이 실제 12화면 중 11개에 있는데 Figma 엔 0개 — 이건 데모 내용 차이로 설명되지 않는
계통적 치환이라 바로 드러났다.

### 픽셀 프로파일

특정 요소는 좌표를 찍어 값을 직접 잰다. 다이얼 그라데이션은 이 방법으로 규약을 확정했고
(최상단 중앙 `#FFF6CC`, 투명 도달 반경 185px ≈ CSS 예측 182px), 튜토리얼 딤도
`255×0.45 + 15×0.55 = 123` 계산과 실측 `(123,125,134)` 가 일치해 alpha 0.55 를 확정했다.

스크린샷은 CDP `Emulation.setDeviceMetricsOverride` 로 2x 캡처한다. `--window-size` 만으로는
macOS 헤드리스에서 레이아웃 뷰포트가 클램프돼 폭이 틀어진다.

### Figma API 함정

- **`gradientTransform` 은 "오브젝트 → 그라데이션" 역방향이다.** 중심 `(cx,cy)`·반지름 `(rx,ry)` 를
  두려면 `a=0.5/rx, e=0.5-a·cx, d=0.5/ry, f=0.5-d·cy` → `[[a,0,e],[0,d,f]]`.
  정방향으로 넣으면 중심이 뒤집힌다. 항등행렬은 두 해석이 같아 구분되지 않는다.
- **`setBoundVariableForPaint` 는 `opacity` 를 버린다.** 바인딩을 먼저 걸고 alpha 를 나중에 얹어야 한다.
- **`resize()` 는 auto-layout 의 hug 를 FIXED 로 덮어쓴다.** 리사이즈 후 `primaryAxisSizingMode` 를
  다시 `AUTO` 로 돌려야 한다.
- **`upload_assets` 는 이미지를 올리지만 캔버스에 배치하지 않을 수 있다.** `nodeId` 를 주고
  `success: true` + `imageHash` 를 받아도 대상 노드의 fill 이 그대로였다(다른 페이지에도 새 노드
  없음). 다행히 **`imageHash` 는 PNG 의 SHA-1** 이라, 로컬에서 `shasum -a 1` 로 계산해
  `fills = [{ type: 'IMAGE', scaleMode: 'FILL', imageHash }]` 로 직접 지정하면 붙는다.
  이미지 자체는 파일 저장소에 정상적으로 올라가 있다.
- **텍스트 노드 높이는 정수로 반올림된다.** 행높이를 `155%` 로 주든 `PIXELS 21.7` 로 주든
  `node.height` 는 22 다. 소수 픽셀이 필요한 패리티는 여기서 막힌다(§9).
- **절대배치 자식은 부모가 리사이즈돼도 따라오지 않는다.** `constraints` 를 `MAX` 로 주지 않으면
  좌측에 고정된다. 오토레이아웃 밖에 얹은 오버레이(아바타 이니셜 등)는 아예 제약이 없어
  부모의 `absoluteBoundingBox` 를 읽어 매번 다시 씌워야 한다.
- **컴포넌트 수정이 전파되는지 확인하려면 `type === 'INSTANCE'` 를 본다.** 이름이 같아도 분리된
  프레임이면 전파되지 않는다. `component.instances` 로 실제 인스턴스 목록을 뽑는 편이 안전하다.
- **복제 직후에는 인스턴스 하위 노드에 쓰지 말 것.** 컴포넌트를 `clone()` 한 뒤 같은 호출에서
  아이콘 인스턴스 안 VECTOR 의 `strokes` 를 칠했더니 **TEXT 는 바뀌고 VECTOR 만 원래 색으로
  되돌아갔다.** 에러도 없었다. 같은 코드를 별도 `use_figma` 호출에서 다시 돌리자 정상 반영됐다
  (10건). 복제본의 인스턴스 하위 트리가 아직 확정되지 않은 것으로 보인다 — **복제와 하위
  오버라이드는 호출을 나눈다.**
- **좌표계를 섞지 말 것.** `node.x` 는 부모 기준이다. 조상이 다른 두 노드의 `x` 를 빼면
  의미 없는 값이 나온다 — 이번에도 정렬이 틀린 줄 알고 한참 봤다. 페이지 기준이 필요하면
  `absoluteBoundingBox` 를 쓴다.

## 7. 행간 — 어디까지 적용했고 왜 거기까지인가

### 패리티 문제가 아니었다

처음엔 "빌드는 `body` 1.55 인데 Figma 는 자동(≈1.19)이라 파일 전역이 틀렸다"고 봤다. **틀린
진단이다.** `line-height: 1.55` 는 앱 UI 에 걸리는 값이고, 문서 페이지의 설명문("색 토큰 38종의
hex·용도와…")은 Figma 에서 쓴 산문이라 빌드에 대응 텍스트가 없다. 거기에 1.55 를 넣어도
패리티는 그대로다.

실제로 패리티가 걸려 있던 건 **W-02 빈 상태**(다중 행 앱 본문) 하나였고 §2.4 에서 해결했다.

### 적용 범위

그래서 남은 적용은 **가독성 개선**으로 성격을 바꿔 문서 페이지에만 했다. 텍스트 432개.

| LN 00 | 101 | 1698 → 1882 |
| LN 01 | 156 | 3213 → 3540 |
| LN 02 | 90 | 1720 → 1940 |

간격이라 특히 필요했다). 5개 페이지 모두 겹침 0.

### 화면 페이지는 제외했다 — 측정 근거

적용 전에 화면을 복제해 `155%` 를 넣고 재본 뒤 복제본을 지우는 방식으로 영향을 실측했다.

## 8. as-built 동기화 — 코드가 바뀌면 Figma 를 따라 고친다

이 파일은 빌드를 문서화한 명세다. 그래서 **UI 코드가 배포되면 Figma 도 같이 갱신해야 한다.**
안 하면 파일이 "코드가 유일한 출처" 라고 적어둔 채로 코드와 어긋난 상태가 된다.

### 제안은 별도 페이지에서 (LN 09)

참고 UI 를 번안한 제안은 **LN 09 · 제안** 에 둔다. LN 05·06(as-built)에 직접 그리면 아직
구현되지 않은 것을 이미 빌드된 것처럼 기록하게 된다. 구현·배포된 뒤에 LN 05·06 으로 옮긴다.

```
참고 UI → LN 09 제안 → 구현·배포 → LN 05·06 as-built 갱신 → LN 07 재캡처
```

### 갱신 절차

1. **컴포넌트부터 고친다.** LN 04 의 회의 카드·FAB 등을 고치면 인스턴스로 전파돼 화면을 하나씩
   손대지 않아도 된다.
2. **좌표는 CSS 에서 계산하고 실측으로 확인한다.** 예: FAB 는 `844 − 56(탭바) − 16 − 64 = 708`,
   `(390 − 64) / 2 = 163`. 로컬 빌드 실측도 `(163, 708)` 이었다.
3. **LN 07 은 영향받은 장만 다시 찍는다.** 라우트가 안 변한 화면(`new`·`detail`)은 그대로 두고,
   섹션 이름에 어느 날짜 캡처가 섞여 있는지 적는다.
4. **캡처 데이터를 기존과 맞춘다.** LN 07 은 '실제 빌드' 페이지라 데모 데이터가 달라지면
   변경과 무관한 차이가 섞여 대조가 어려워진다.

### 1차 갱신 (2026-07-29) — 구현 반영

구현된 3건을 반영했다 — 목록 우측 녹음 길이 · FAB 하단 중앙 64px · 선택 모드.

| 대상 | 내용 |
|---|---|
| LN 04 회의 카드 | 날짜줄에서 길이 제거, 우측에 `45:30`(`ink/500` 11px) 추가 |
| LN 04 FAB | `56×31` + `+` 텍스트 → `64×64` 원형 + `index.html:72` plus SVG |
| LN 05 FAB 위치 | 5개 화면 `(318, 708)` → `(163, 708)` |
| LN 05 M-01 헤더 | 벨 · 선택 · 새 회의 버튼 추가 |
| LN 07 | 영향받은 7장 재캡처(모바일 5 · 웹 2), 나머지 7장 유지 |

**함께 드러난 기존 누락 2건**

- 마이페이지·알림함에 FAB 가 없었다. `.tab-fab` 은 `new`·`detail` 에서만 숨으므로 이 두 화면에도
  떠야 한다.
- M-01 헤더에 우측 버튼군(벨·새 회의)이 통째로 없었다. 선택 버튼만 넣으면 카운트 옆에 붙어
  실제와 다른 자리가 되므로 셋 다 넣었다.

둘 다 이번 코드 변경과 무관한, 처음부터 있던 차이다. 화면을 손대는 김에 실측과 대조해서
드러났다 — §6 의 팔레트 대조와 같은 성격이다.

### 제안 페이지에 구현 상태를 적을 때는 코드를 읽는다

LN 09 주석에 *"상세 요약: `summary_versions` 에 타임스탬프가 없다. 스키마·프롬프트 변경이
필요하다"* 라고 적어뒀는데 **사실이 아니었다.** `summary_sections` 의 `start_ms`·`end_ms` 는
「타임스탬프 앵커 구간 요약」부터 있었고, 제공자가 전사 구간의 실제 시각을 붙여 저장하며
프런트는 시각 칩으로 그 지점부터 재생까지 한다.

실제 차이는 **위치뿐**이었다 — 요약이 오프캔버스 드로어 안에 있어 `#/meetings/{id}/summary`
로 들어와도 전사가 보였다. URL 이 탭을 가리키면 드로어를 열도록 한 프런트 10줄로 끝났다.

화면을 보고 "이 기능은 없다" 고 넘겨짚은 게 원인이다. 주석은 나중에 일정 산정의 근거가 되므로
**구현 상태는 반드시 코드에서 확인하고 적는다.** 해당 주석은 「구현 결과」로 다시 썼다.

### 2차 갱신 (2026-07-29) — 치수 감사

LN 09 를 스크린샷으로 점검하다 **탭바가 실제보다 8px 두꺼운 것**을 발견했고, 원인을 좇으니
목록·카드 전반의 치수가 어긋나 있었다. §1~§7 은 전부 **색** 작업이었다. 색은 팔레트 대조로
끝까지 훑었지만 **치수는 아무도 재지 않았다** — 색 감사를 통과했다고 치수가 맞는 게 아니다.

기준값은 프로덕션 앱을 390×844 로 열어 `getBoundingClientRect` · `getComputedStyle` 로 떴다.
LN 07 캡처와 같은 환경이라 `env(safe-area-inset-bottom)` 은 0 이다.

#### 탭바 — 컴포넌트 하나가 10개 화면을 밀고 있었다

`탭바 / 홈 선택` 이 64px 였다. 내부는 패딩 8 + 콘텐츠 39 + 8 = 55 인데 `counterAxisSizingMode`
가 FIXED 64 라 9px 이 붕 떠 있었다. CSS 는 `height: calc(56px + env(safe-area-inset-bottom))` 이고
실측도 56 이다. 64 는 56 도 90(56+34)도 아니라 어느 해석으로도 설명되지 않는다.

| | 실제 빌드 | 이전 | 이후 |
|---|---|---|---|
| 탭바 | `y 788 · h 56` | `y 780 · h 64` | `y 788 · h 56` |
| FAB | `x 163 · y 708` | LN 05 708 / LN 09 **700** | 708 |
| FAB↔탭바 | 16 | LN 05 8 / LN 09 16 | 16 |

증상은 페이지마다 달랐지만 원인은 하나였다. LN 05 는 FAB 절대 위치가 맞는 대신 간격이 좁았고,
LN 09 는 간격을 맞추다 탭바의 오차를 흡수해 위치가 틀어졌다.

높이 56 + `counterAxisAlignItems: CENTER`(자식 y=8.5 — 빌드의 `.tab-btn { justify-content: center }`)
로 고치고, 인스턴스 10개를 `y 780→788`, `스크롤` 프레임을 `780→788` 로 맞췄다. **화면 프레임은
`layoutMode: NONE`(절대 배치)이라 컴포넌트를 고쳐도 인스턴스 y 는 따라오지 않는다.**

#### 회의 카드 — 잘못된 값들이 서로 상쇄돼 있었다

카드 높이가 91 로 빌드(91.3)와 맞아 보였는데, 타이포를 고치자 92 가 됐다. 맞아 보이던 91 은
**틀린 값들이 우연히 상쇄된 결과**였다.

| 항목 | 이전 | 이후 | 빌드 |
|---|---|---|---|
| 제목 | 13.5 · `ink/900` | 14 · `ink/950` | 14 / 700 / `#0F1222` |
| 날짜 | 11.5 | 12 | 12 |
| 행높이 | AUTO (17 / 14) | 155% (22 / 19) | 21.7 / 18.6 |
| 패딩 | 14 / 14 | 11 / 10 | `11px 10px` |
| 아바타 | 40 | 42 | 42 |
| 아바타↔본문 | 12 | 11 | 11 |
| 제목↔날짜 | 6 | 2 | 2 |
| 날짜↔칩 | 6 | 7 | 7 |
| 칩 높이 · 간격 · 좌우패딩 | 21 · 6 · 9 | 20 · 5 · 8 | 20 · 5 · 8 |
| 카드 폭 | 360 | 369 | 369 |

빌드 구성은 `11 + 21.7 + 2 + 18.6 + 7 + 20 + 11 = 91.3` 이다. Figma 의 세로 auto-layout 은
gap 이 하나뿐이라 2 와 7 을 동시에 낼 수 없어, `본문` gap 을 2 로 두고 `태그` 프레임에
`paddingTop: 5` 를 얹어 7 을 만들었다.

#### 목록 컨테이너 — 패딩이 컨테이너마다 다르다

Figma 는 15/20/18 로 뭉뚱그려져 있었는데 CSS 는 화면마다 다르다.

| 화면 | 이전 | 이후 | CSS |
|---|---|---|---|
| M-01 홈 | 15 | 10 | `.list-scroll` `4px 10px` |
| M-02·03·04·튜토리얼 | 20 | 16 | `.compose-scroll` `18px 16px` |
| 폴더 | 18 | 18 ✓ | `.folder-page` `20px 18px` |
| 마이 · 알림 | 18 | 16 | `.mypage/.notif-page` `18px 16px` |
| 달력 | 18 | 14 | `.cal-page` `18px 14px` |

M-01 스크롤은 **389** 로 줄이고 우측에 1px `border/base` 스트로크를 넣었다 —
`.col-list { border-right: 1px }` 때문에 내용 폭이 390 이 아니라 389 이고, 그래야
`389 − 10 − 10 = 369` 가 나온다. 홈 배너는 `margin: 4px 8px 12px` 라 353 이므로 고정폭으로
빼고 스크롤을 가운데 정렬했다(FILL 자식은 정렬과 무관하게 꽉 차므로 나머지는 영향 없음).

#### LN 06 웹 목록 — 한 줄이었다

`제목` / `날짜 · 길이` 한 줄 구조에 6개 항목이 전부 `45:30` 이었다. 빌드는 모바일과 같은
`listItemHtml` 을 써서 2줄이다.

```
[아바타] 제목 ───────────── 45:30      .list-item-top (flex, baseline, gap 8)
         2026.07.27 (월)                .list-item-sub (margin-top 2)
```

항목 12개(2화면 × 6)를 재구성하고 타이포를 실측값(14/`ink/950` · 11/`ink/500` · 12/`ink/500`)에
맞췄다. 제목을 FILL(`flex:1`), 길이를 HUG(`flex:none`)로 둬 길이가 우측 끝에 붙는다.

#### 절대배치가 두 번 발목을 잡았다

- **길이 텍스트.** 좌표 고정이라 `1:02:40` 처럼 자릿수가 늘면 오른쪽으로 밀려 카드 밖으로
  나갔다. 폭 60 고정 + 우측 정렬로 바꿨다. 카드 폭이 360→369 로 커졌을 때도 좌측 앵커(`MIN`)라
  여백이 19 가 됐다 — 제약을 `MAX` 로 바꿔 폭과 무관하게 10 을 유지한다.
- **아바타 이니셜.** 화자별 색이 달라 카드 컴포넌트 밖 절대배치 텍스트로 얹혀 있다. 원의
  크기·위치가 바뀔 때마다 따라오지 않아 세 번 재정렬했다. 원의 `absoluteBoundingBox` 를 읽어
  그대로 씌우는 방식이 확실하다.

#### LN 09 카드는 인스턴스가 아니었다

컴포넌트를 고치면 LN 05·LN 09 양쪽에 전파될 것으로 봤는데, LN 09 의 카드는 **분리된 프레임**
이라 전파되지 않았다(제안을 만들며 구조를 바꾸느라 detach 했다). 같은 값을 직접 넣어야 했다.
**전파를 전제하기 전에 `type === 'INSTANCE'` 를 확인할 것.**

#### 탭바 활성 탭 — 9화면 중 8화면이 홈을 켜고 있었다

탭바가 변이 없는 **단일 컴포넌트 `탭바 / 홈 선택`** 이라 인스턴스 10개가 전부 같은 상태였다.
폴더 화면에서도, 달력 화면에서도, 마이페이지에서도 홈이 켜져 있었다. 색 자체는 맞았다 —
활성 `brand/700` · 비활성 `ink/400` 으로 `.tab-btn.is-active` 와 일치한다. 틀린 건 **어느 탭이
켜지느냐** 였다.

```js
// app.js:695-700
document.querySelectorAll('[data-nav]').forEach(a => a.classList.remove('is-active'));
var map = { list:'home', detail:'home', calendar:'calendar', folders:'folders', me:'me' };
var key = map[route.name];
if (!key) return;   // ← 제거를 먼저 하고 반환한다
```

`new` 와 `notifications` 는 map 에 없다. **이전 탭이 유지되는 게 아니라 아무 탭도 안 켜진다** —
제거가 반환보다 앞이기 때문이다.

속성 `활성` 5종(`홈`·`폴더`·`달력`·`마이`·`없음`)의 변이 세트로 바꾸고 라우트대로 지정했다.

| 화면 | 라우트 | 변이 |
|---|---|---|
| M-01 홈 | `list` | 홈 |
| M-02 · M-03 · M-04 · 튜토리얼 | `new` | 없음 |

## 9. 남은 차이 — 고치지 않았다

| 차이 | 이유 |
|---|---|
| 화면 페이지 행간이 Figma 자동 | §7 참조. 3화면이 잘리고, 패리티 이득이 없다 |
| LN 08 바운딩 겹침 2건 | 렌더 충돌 없음. 아카이브 레이아웃을 건드리지 않는다 |

| 카드 높이 92 vs 빌드 91.3 | Figma 가 텍스트 높이를 정수로 반올림한다(21.7→22, 18.6→19). 행높이를 `PIXELS 21.7` 로 직접 줘도 같다 |
| 칩에 `.chip-dot` 없음 | 치수가 아니라 구조. 상태 칩 앞의 점 |
| LN 06 항목에 상태 칩 줄 없음 | 빌드 항목은 91px(칩 포함), Figma 는 53px |
| LN 05 헤더·검색이 스크롤 안에 있음 | 빌드는 `.list-scroll` 의 형제라 패딩을 안 받고 389 폭이다 |
| 튜토리얼 스포트라이트 피연산자 2개가 미바인딩 | `figma.subtract` 의 입력 사각형이 Figma 기본 `#D9D9D9` 를 달고 있다. 실제로 칠해지는 건 불리언 노드 자신의 `ink/950 @ 55%` 이고 그건 바인딩돼 있어 렌더에 영향이 없다 |
| LN 04 `아이콘 시트 · 26종` SECTION 이 미바인딩 | SECTION 노드 자체의 배경·테두리다. Figma 섹션의 기본 스타일이지 UI 콘텐츠가 아니다 |

마지막 두 항목은 §6 의 미바인딩 감사가 **불리언 노드 내부와 SECTION 을 안 봤다**는 뜻이기도
하다. "미바인딩 0" 은 렌더되는 UI 페인트 기준이었다.
