## 1. Phase 3 목표 및 범위

### 1.1 핵심 목표

Phase 3는 MediWay가 **가상 데이터에서 실제 병원 환경**으로 전환하는 결정적 단계입니다.
Phase 1-2에서 검증한 기술을 실제 대구·경북 지역 병원에 배포하여,
현실 환경에서의 동작 검증과 환자·의료진 피드백을 수집합니다.

```
목표 1: 병원 협업 확보
  — 대구·경북 지역 1~2개 병원과 파일럿 협약 체결
  — 병원 IT팀, 시설팀, 간호부서와 협력 체계 구축

목표 2: 실제 병원 인프라 구축
  — 실제 병원 평면도 데이터 확보 및 디지털화
  — BLE 비콘 현장 설치 및 캘리브레이션 (파일럿 구역)
  — 1~3m 정확도의 실시간 블루닷 네비게이션 실현

목표 3: 실환자 사용성 검증
  — 실제 환자/보호자 대상 사용성 테스트 (30~50명)
  — 정량적·정성적 데이터 수집 및 분석
  — 이동 시간 30% 단축 목표 검증

목표 4: 서비스 안정성 확보
  — Firebase 직접 접근 → API 서버 도입
  — 모니터링, 로깅, 에러 추적 체계 구축
  — 동시 접속 50~100명 처리 가능
```

### 1.2 구현 범위 (In-Scope)

```
인프라:
  ✅ 파일럿 병원 1개 건물, 2~3개 층 대상
  ✅ BLE 비콘 20~50개 설치
  ✅ 실제 병원 평면도 → SVG/이미지 맵 변환
  ✅ 네비게이션 그래프 실측 데이터 기반 구축

앱 기능:
  ✅ 실시간 블루닷 네비게이션 (BLE 비콘 기반, 1~3m 정확도)
  ✅ 턴바이턴 텍스트 안내 ("10m 앞에서 우회전")
  ✅ 자동 도착 감지 (수동 버튼 폴백 유지)
  ✅ 층 자동 감지 (비콘 Major 값 기반)
  ✅ 자유 네비게이션 (목적지 검색 → 경로 안내)
  ✅ 주차 위치 기록 (수동 입력 방식)
  ✅ 의료진 앱 — 실제 진료과별 동선 템플릿

백엔드:
  ✅ Node.js/Express API 서버 (또는 Firebase Cloud Functions)
  ✅ 서버 사이드 FCM 푸시 발송
  ✅ 관리자 대시보드 (비콘 상태, 세션 모니터링)
  ✅ 익명화 동선 분석 데이터 수집 (opt-in)

운영:
  ✅ 사용성 테스트 설계 및 실행
  ✅ 피드백 수집 체계 (인앱 + 인터뷰)
  ✅ 에러 모니터링 (Sentry / Firebase Crashlytics)
```

### 1.3 구현 범위 밖 (Out-of-Scope)

```
  ❌ AR 카메라 뷰 네비게이션 (Phase 4)
  ❌ 다병원 동시 운영 / SaaS 전환 (Phase 4)
  ❌ 주차 정산 시스템 연동 (Phase 4)
  ❌ EMR/HIS 시스템 연동 (Phase 4)
  ❌ App Store 정식 배포 (TestFlight 유지)
  ❌ Android 앱
  ❌ 다국어 지원
  ❌ AI 동선 추천
```

### 1.4 네비게이션 레벨 목표

```
Phase 2까지 달성:
  Level 1 ✅ — 정적 경로 안내
  Level 2 △ — BLE 프로토타입 (제한 공간)

Phase 3에서 달성 목표:
  Level 2 ✅ — 대략적 위치 감지 (층 감지 + 구역 파악)
  Level 3 ✅ — BLE 비콘 실시간 네비게이션 (파일럿 구역)
    • 1~3m 정확도의 블루닷
    • 턴바이턴 텍스트 안내
    • 자동 도착 감지
    • 층 자동 전환

Level 4 (AR)는 Phase 4로 유보
```

## 2. Phase 2 대비 변경점 — 프로토타입에서 파일럿으로

### 2.1 환경 변화

```
항목              Phase 2 (프로토타입)         Phase 3 (파일럿)
────────────────────────────────────────────────────────────────
병원 데이터       가상 병원 (하드코딩)          실제 병원 평면도
비콘 수           3~4개 (테스트 공간)          20~50개 (병원 구역)
사용자            개발자 본인                   실제 환자/간호사 30~50명
서버              Firebase 직접 접근            API 서버 + Firebase
동시 접속         1~2명                        50~100명
에러 처리         콘솔 로그                     Sentry + Crashlytics
지도 데이터       번들 내 정적 파일             서버에서 병원별 다운로드
동선 템플릿       개발자 정의                   간호사와 협의하여 정의
```

### 2.2 코드 아키텍처 전환

```
Phase 2 아키텍처:
  iOS 앱 ←→ Firebase Realtime DB (직접 접근)

Phase 3 아키텍처:
  iOS 앱 ←→ API 서버 ←→ Firebase / 자체 DB
  웹 앱  ←→ API 서버 ←→ Firebase / 자체 DB
  관리자 대시보드 ←→ API 서버

API 서버 도입 이유:
  1. 보안: 클라이언트에서 DB 직접 접근 제거
  2. 비즈니스 로직 중앙화: 세션 생성/검증/만료 서버 측 처리
  3. FCM 푸시: 서버 사이드 발송으로 전환
  4. 분석 데이터: 익명화 파이프라인 서버 측 처리
  5. 다병원 대응: 병원별 데이터 격리 및 인증

Phase 2 → Phase 3 마이그레이션:
  - SessionService의 Firebase 직접 호출 → API 호출로 교체
  - MapDataProvider의 BundledMapDataProvider → RemoteMapDataProvider 교체
  - PositionProvider 인터페이스는 유지, BLE 로직 확장
  - Phase 2에서 설계한 프로토콜 추상화 덕분에 교체 범위 최소화
```

## 3. 병원 협업 전략

### 3.1 대상 병원 후보

```
1순위: 경북대학교병원
  - 소재지: 대구광역시 중구
  - 규모: 상급종합병원, 약 900병상
  - 접근성: 경북대 소속이므로 산학협력 채널 활용 가능
  - 접점: 산학협력단, 의료정보팀, 혁신의료센터

2순위: 영남대학교병원
  - 소재지: 대구광역시 남구
  - 규모: 상급종합병원, 약 900병상
  - 접근성: 대구 지역 대학병원으로 산학협력 가능
  - 접점: 의료정보팀, 경영혁신실

3순위: 칠곡경북대학교병원
  - 소재지: 대구광역시 북구
  - 규모: 종합병원, 약 600병상
  - 접근성: 경북대 부속이므로 본원 협력 시 연계 용이
  - 비교적 신축으로 시설 구조가 깔끔할 수 있음

백업: 대구가톨릭대학교병원, 계명대학교 동산병원
```

### 3.2 협업 제안서 구성

```
제안서 핵심 구성 (5~10페이지):

1. 문제 정의
   - 환자 동선 안내 부재 현황
   - 해외 병원 도입 사례 (Kontakt.io, infsoft)
   - 환자 만족도 영향 데이터

2. 솔루션 소개
   - MediWay 데모 영상/스크린샷
   - 의료진 3탭 동선 전송 시연
   - BLE 비콘 실내 네비게이션 데모

3. 파일럿 계획
   - 범위: 1개 건물, 2~3개 층, 외래 진료 구역
   - 기간: 3개월 (설치 1개월 + 운영 2개월)
   - 비콘 설치: 병원 측 시설팀 협조 필요 사항
   - 환자 참여: 30~50명, 자발적 참여, 동의서

4. 병원 측 부담
   - 비콘 설치 위치 협의 및 승인
   - 건물 평면도(CAD) 제공
   - 간호사 2~3명 앱 사용 교육 (1시간)
   - 환자 모집 협조 (외래 진료 시 안내)

5. 기대 효과
   - 환자 이동 시간 단축 (해외 사례 30%)
   - 길 안내 반복 질문 감소
   - 환자 만족도 향상 데이터 확보
   - 병원 혁신 사례로 홍보 가능

6. 개인정보보호 보장
   - 의료 정보 비접촉
   - 위치 데이터 비저장
   - 익명 인증만 사용
   - 실험 종료 후 모든 데이터 삭제

7. 개발자/팀 소개
   - 경북대학교 소속
   - Phase 1-2 기술 검증 완료 내역
   - 기술 역량 (풀스택, 모바일, BLE)
```

### 3.3 협업 접근 채널

```
경로 1: 산학협력단 (가장 공식적)
  경북대학교 산학협력단 → 경북대병원 의료정보팀 연결
  - 장점: 공식 채널, 보험/법적 커버 가능
  - 소요: 1~2개월 (행정 절차)

경로 2: 지도교수 연결 (가장 현실적)
  통계학과 지도교수 → 의과대학/병원 관련 교수 소개
  - 장점: 비교적 빠른 접근
  - 소요: 2~4주

경로 3: KDT 과정 멘토/네트워크
  KDT 12기 운영기관 → 산업체 멘토 → 병원 관계자
  - 장점: 실무 네트워크 활용
  - 소요: 2~4주

경로 4: 병원 혁신 부서 직접 연락
  경북대병원 혁신의료센터, 의료질관리팀 등에 직접 제안
  - 장점: 의사결정자에게 직접 접근
  - 리스크: cold outreach이므로 응답률 낮을 수 있음

권장 전략:
  경로 1~3을 병행 추진하되,
  경로 2(지도교수 연결)를 우선적으로 시도
```

### 3.4 병원 내 협력 부서 및 역할

## 4. 법적·윤리적 준비사항

### 4.1 IRB 심의 필요성 판단

```
MediWay 파일럿이 IRB 심의를 받아야 하는지 판단 기준:

IRB 심의 대상:
  "사람을 대상으로 물리적으로 개입하거나, 의사소통·대인접촉 등의 
   상호작용을 통하여 수행하는 연구, 또는 개인을 식별할 수 있는 
   정보를 이용하는 연구" — 생명윤리법 제2조

MediWay 파일럿의 성격:
  ✅ 사람(환자)과 상호작용 있음 → 해당
  ✅ 위치 데이터 수집 (익명이어도) → 해당 가능성
  ✅ 사용성 설문/인터뷰 수행 → 해당

결론: IRB 심의를 받는 것이 안전합니다.

IRB 신청 시 준비 서류:
  □ 연구계획서 (파일럿 목적, 방법, 기간)
  □ 참여자 동의서 양식
  □ 참여자 모집 공고문
  □ 개인정보 처리 계획서
  □ 데이터 관리 계획 (수집, 저장, 삭제)
  □ 연구자 CITI 교육 이수 증명
  □ 지도교수 서명 (학생 연구자인 경우)

IRB 예상 소요 기간: 2~4주 (경북대 기준, 신속심의 가능)
```

### 4.2 환자 참여 동의서 핵심 항목

```
동의서에 반드시 포함할 내용:

1. 연구 목적
   "본 연구는 병원 내 환자 동선 안내 앱의 유용성을 검증하기 위한
```

### 6.1 비콘 수량 산정

```

  - 삼변측량에 최소 3개 비콘이 동시 수신되어야 함
  - 실내 BLE 유효 수신 범위: 약 10~15m (환경에 따라 변동)

층별 예상 비콘 수:
```

## 7. 비콘 캘리브레이션 시스템

### 7.1 캘리브레이션 목적

```
캘리브레이션이 필요한 이유:
  - RSSI 값은 환경에 따라 크게 변동 (벽, 인체, 가구, 금속)
  - Phase 2의 기본 txPower(-59), n(2.5) 값은 이론값
  - 실제 병원 환경에서는 구역별로 전파 특성이 다름
  - 정확한 위치 추정을 위해 환경 특화 파라미터 필요

캘리브레이션으로 결정할 파라미터:
  1. 각 비콘의 txPower (1m 기준 RSSI)
  2. 구역별 경로 손실 지수 n
  3. 비콘별 RSSI 오프셋 (개체 차이 보정)
```

### 7.2 캘리브레이션 도구 앱 개발

```
캘리브레이션 전용 iOS 앱 (또는 기존 앱 내 숨김 메뉴):

기능:
  1. 특정 비콘 선택 → 1m/2m/3m/5m 거리에서 RSSI 연속 측정
  2. 측정 데이터 CSV 내보내기
  3. txPower, n 값 자동 피팅 (회귀 분석)
  4. 피팅 결과를 비콘 설정 파일에 저장

측정 프로토콜:
  1. 비콘 앞 1m 지점에 서서 30초간 RSSI 수집 (약 300개 샘플)
  2. 2m 지점 → 30초 수집
  3. 3m 지점 → 30초 수집
  4. 5m 지점 → 30초 수집
  5. (선택) 8m, 10m 지점

자동 피팅:
  RSSI = txPower - 10 * n * log10(distance)

  수집된 (distance, RSSI) 쌍으로 선형 회귀:
    y = RSSI
    x = -10 * log10(distance)
    → y = txPower + n * x
    → 기울기 = n, 절편 = txPower

구현 위치: CalibrationService.swift (별도 타겟 또는 숨김 메뉴)
```

### 7.3 캘리브레이션 데이터 구조

```swift
// 캘리브레이션 결과 데이터

struct BeaconCalibration: Codable {
    let beaconId: String          // "B1_F2_101"
    let major: Int                 // 2 (층)
    let minor: Int                 // 101
    let installedPosition: Coordinate  // 설치 위치 (x, y)
    let floorLevel: Int            // 2

    // 캘리브레이션 결과
    let txPower: Double            // -62.3 (실측)
    let pathLossExponent: Double   // 2.8 (실측)
    let rssiOffset: Double         // -1.5 (개체 보정)

    // 메타데이터
    let calibratedAt: Date
    let environment: String        // "복도", "진료실 앞", "로비"
    let notes: String?
}

// 전체 캘리브레이션 설정 파일
struct CalibrationConfig: Codable {
    let hospitalId: String
    let version: Int
    let beacons: [BeaconCalibration]
    let updatedAt: Date
}

// 서버에 저장, 앱에서 다운로드하여 BeaconService에 적용
// API: GET /api/hospitals/:hospitalId/beacon-calibration
```

### 7.4 RSSI 핑거프린팅 (고급, 선택)

```
삼변측량 보완을 위한 핑거프린팅 기법:

개념:
  특정 위치에서 모든 비콘의 RSSI 조합을 "지문"으로 기록.
  새로운 RSSI 조합이 들어오면, 가장 유사한 지문의 위치로 추정.

수집 방법 (오프라인 학습):
  1. 파일럿 구역을 2m × 2m 그리드로 나눔
  2. 각 그리드 지점에서 30초간 모든 비콘의 RSSI 수집
  3. (위치, RSSI벡터) 쌍을 핑거프린트 DB에 저장

추정 방법 (온라인):
```

```typescript
// functions/src/index.ts — Firebase Cloud Functions

import { onRequest } from 'firebase-functions/v2/https';
import { getDatabase } from 'firebase-admin/database';
import { getMessaging } from 'firebase-admin/messaging';
import { initializeApp } from 'firebase-admin/app';

initializeApp();

const db = getDatabase();

// 세션 생성
export const createSession = onRequest(async (req, res) => {
    if (req.method !== 'POST') { res.status(405).send('Method Not Allowed'); return; }

    const { staffUid, patientUid, qrToken, waypoints, hospitalId } = req.body;

    // 1. QR 토큰 검증
    const tokenSnap = await db.ref(`qr_tokens/${qrToken}`).get();
    if (!tokenSnap.exists() || tokenSnap.val().status !== 'waiting') {
        res.status(400).json({ error: 'Invalid or expired QR token' });
        return;
    }

    // 2. 세션 생성
    const sessionId = crypto.randomUUID();
    const session = {
        sessionId, staffUid, patientUid, qrToken,
        waypoints, currentWaypointIndex: 0,
        status: 'navigating', hospitalId,
        createdAt: Date.now(),
    };
    await db.ref(`sessions/${sessionId}`).set(session);

    // 3. QR 토큰 매칭 상태 업데이트
    await db.ref(`qr_tokens/${qrToken}`).update({
        status: 'matched', sessionId,
    });

    // 4. 환자에게 푸시 알림 (서버 사이드 FCM)
    const fcmToken = tokenSnap.val().fcmToken;
    if (fcmToken) {
        await getMessaging().send({
            token: fcmToken,
            notification: {
                title: 'MediWay',
                body: `다음 목적지가 등록되었습니다`,
            },
            data: { sessionId, type: 'route_assigned' },
        });
    }

    res.status(201).json({ sessionId, session });
});

// 도착 확인
export const confirmArrival = onRequest(async (req, res) => {
    if (req.method !== 'PATCH') { res.status(405).send('Method Not Allowed'); return; }

    const { sessionId } = req.params;
    const { waypointIndex } = req.body;

    const sessionRef = db.ref(`sessions/${sessionId}`);
    const snap = await sessionRef.get();
    if (!snap.exists()) { res.status(404).json({ error: 'Session not found' }); return; }

    const session = snap.val();
    const nextIndex = waypointIndex + 1;
    const isCompleted = nextIndex >= session.waypoints.length;

    // 세션 업데이트
    const updates: Record<string, any> = {
        [`waypoints/${waypointIndex}/status`]: 'completed',
        [`waypoints/${waypointIndex}/arrivedAt`]: Date.now(),
    };

    if (isCompleted) {
        updates['status'] = 'completed';
        updates['completedAt'] = Date.now();
    } else {
        updates['currentWaypointIndex'] = nextIndex;
        updates[`waypoints/${nextIndex}/status`] = 'current';
    }

    await sessionRef.update(updates);

    // 다음 목적지 푸시 또는 완료 푸시
    const fcmToken = session.fcmToken;
    if (fcmToken) {
        const message = isCompleted
            ? '오늘 진료가 모두 끝났습니다. 귀가하셔도 됩니다.'
            : `다음 목적지로 이동해주세요`;
        await getMessaging().send({
            token: fcmToken,
            notification: { title: 'MediWay', body: message },
            data: { sessionId, type: isCompleted ? 'route_completed' : 'next_waypoint' },
        });
    }

    res.json({ success: true, isCompleted, nextIndex: isCompleted ? null : nextIndex });
});
```

### 10.2 방향 계산 알고리즘

```swift
// 경로 세그먼트에서 방향 전환 감지

struct TurnInstruction {
    enum TurnType {
        case straight       // 직진
        case turnLeft       // 좌회전
        case turnRight      // 우회전
        case slightLeft     // 약간 왼쪽
        case slightRight    // 약간 오른쪽
        case uTurn          // 유턴
        case floorChange(via: String, toFloor: Int)  // 층 이동
        case arrival        // 도착
    }

    let type: TurnType
    let distanceToNext: Double    // 다음 안내까지 거리 (미터)
    let instruction: String       // 표시할 텍스트
    let coordinate: Coordinate    // 안내 발생 좌표
}

// 방향 전환 계산
func calculateTurn(from: Coordinate, via: Coordinate, to: Coordinate) -> TurnType {
    // 두 벡터 간 각도 계산
    let angle1 = atan2(via.y - from.y, via.x - from.x)
    let angle2 = atan2(to.y - via.y, to.x - via.x)
    var turnAngle = angle2 - angle1

    // -π ~ π 범위로 정규화
    while turnAngle > .pi { turnAngle -= 2 * .pi }
    while turnAngle < -.pi { turnAngle += 2 * .pi }

    let degrees = turnAngle * 180 / .pi

    switch degrees {
    case -30...30:      return .straight
    case 30...80:       return .slightRight
    case 80...170:      return .turnRight
    case -80..<(-30):   return .slightLeft
    case -170..<(-80):  return .turnLeft
    default:            return .uTurn
    }
}
```

```
    - 총 이동 시간 (진료과 A 출발 → 약국 도착)
    - 경유지당 이동 시간
    - 길 묻는 횟수 (관찰자 기록)
    - 경로 이탈 횟수 (앱 로그)
    - 작업 완료율 (모든 경유지 방문 성공 여부)

  정성적 지표:
    - SUS (System Usability Scale, 10문항)
    - 만족도 설문 (5점 리커트)
    - 자유 응답 (불편한 점, 개선 제안)
    - 인터뷰 (선택 참여자 10명)

사전 설문:
  - 연령대, 병원 방문 빈도
  - 스마트폰 숙련도 (1~5점)
  - 이 병원 방문 경험 유무
```
